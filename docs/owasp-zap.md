# Disposable OWASP ZAP environment (SQLite, no installation)

Run these PowerShell commands from the repository root on **`test/owasp-zap`**.
The scripts check the branch; they never switch branches, commit, push, install
packages, contact Supabase, or launch ZAP/scans. Existing `.venv`, Node.js and
`frontend/node_modules` are required. Python 3.12+ is required (verified on 3.14).

## Start, verify, stop and reset

```powershell
# Once; safe to repeat without replacing existing fixtures.
.\scripts\zap.ps1 init

# Keep this terminal open. Wait for both URLs and "Ready".
.\scripts\zap.ps1 start
```

In another PowerShell terminal at the same repository root:

```powershell
.\scripts\zap.ps1 status
.\scripts\zap.ps1 verify

# Stop before resetting. Ctrl+C in the startup terminal also stops both services.
.\scripts\zap.ps1 stop

# Deletes ONLY .zap/state and recreates synthetic data and application secrets.
# This destroys test accounts, MFA enrolments, sessions, uploads, email and audit data.
.\scripts\zap.ps1 reset
.\scripts\zap.ps1 start
```

Open **<https://127.0.0.2:3443/login>**. The API is
**<https://127.0.0.2:8443>**. Both listeners bind only to this loopback IP;
`127.0.0.1:3000` and `127.0.0.1:8000` remain normal development addresses.
Use `127.0.0.2` consistently; do not substitute `localhost`.

The launcher generates a private local CA and server certificate. No certificate
is installed in your computer's trust store. A normal browser may need an explicit
certificate exception for **both** the API (visit `/api/account/csrf/`) and frontend.
Alternatively, trust **only** `.zap/certs/ca.crt` in a dedicated testing browser
profile. Do not import/share `server.key`, and do not disable certificate checking
globally. The built-in verifier trusts this CA explicitly and validates TLS.
Certificates last 180 days; while stopped, remove only `.zap/certs` and run `init`
to regenerate an expired certificate, then update the test browser's trust.

## Accounts, assets and mail

Open `.zap/state/accounts.json` **in your editor**, not in terminal output. It holds
generated passwords for `zap_viewer`, `zap_editor`, and `zap_admin`.
The Admin belongs to the application Admin group and is staff, not a superuser.
All three fixtures have synthetic verified `example.invalid` email addresses.
Their first login requires the application's normal authenticator enrolment;
scan its QR code with an authenticator or use its setup key. No MFA seed, recovery
code, token or password is logged by the setup scripts.

The two seeded PNGs pass the ordinary multipart serializer, quarantine, decoder
subprocess, private file promotion and SHA-256 pipeline. One synthetic tag is
included. Additional upload fixtures are `.zap/state/zap-red-sample.png` and
`.zap/state/zap-blue-sample.png`. Viewer can read approved assets; Editor/Admin
can manage uploads under the existing application permissions.

New signups are restricted to `example.invalid` addresses in this environment and
still require email verification and MFA. Outgoing verification/recovery mail is
written only to `.zap/state/email`. Open these private files in your editor and
use their links; they point to the testing frontend. No SMTP connection is made.
Use the normal forgot-password flow to exercise recovery; reset the whole disposable
environment to recover a lost fixture password/MFA enrolment.

The initializer is idempotent once fixture credentials exist. If initialization
is interrupted between database writes and saving credentials, run `reset` rather
than editing the database or borrowing development records.

## Isolation boundaries

| Component | Dedicated location/configuration |
| --- | --- |
| Database | `.zap/state/zap.sqlite3`; SQLite only; no DB host/credentials |
| Quarantined/approved uploads | `.zap/state/private_assets` |
| Legacy media root (empty) | `.zap/state/media` |
| Upload/decoder temporary files | `.zap/state/tmp` |
| Captured emails | `.zap/state/email` |
| Application/MFA encryption secrets | `.zap/state/secrets.json`; regenerated by reset |
| HTTPS certificates | `.zap/certs`; retained by reset to keep browser trust stable |
| Process logs | `.zap/state/logs` |
| Staged frontend/build cache | `.zap/frontend`; only source/public/config copied |
| Cookies | `zap_access`, `zap_refresh`, `zap_sessionid`, `zap_csrftoken`; host-only |
| Authentication policy | Real `backend.settings`; normal password hashers, MFA, throttles and revocation |

`.zap` is git-ignored. On Windows its ACL grants the current user and SYSTEM access;
on other systems its directory permissions are private. Treat the whole directory,
captured mail, browser profiles and ZAP sessions/reports as sensitive. Do not commit
or share them. No real data is copied into fixtures.

`backend/.env` and frontend development environment files are never loaded by the
launcher. Child processes receive only allowlisted OS runtime variables plus explicit
ZAP settings. Settings reject inherited database/email/auth configuration, require
the dedicated launcher, and assert the SQLite engine, database filename, storage,
email backend, host and secure cookie names/flags. State paths reject traversal,
symlinks, junctions and hard-linked files. Reset holds a lifecycle lock and refuses
to run while this supervisor owns the services. Occupied ports are rejected.

The backend additionally rejects Python outbound socket connections; mail uses a
private file backend. Frontend telemetry is disabled and its testing-only CSP limits
browser connections to the isolated frontend/API. These are application configuration
safeguards, **not an OS/container sandbox against arbitrary native code execution**.
Keep active scans controlled and review payloads that invoke external callbacks.

Security auditing and monitoring still run and write to this SQLite database.
The dedicated TLS adapter adds a non-secret instance fingerprint; startup and live
verification check it to distinguish this state from another listener.
No diagnostic or unauthenticated testing API endpoints are added.

## ZAP: passive scanning and authenticated browsing

1. Start with ZAP in **Safe mode**. Do not use Quick Start's automated attack button.
   Use **Manual Explore** to open a ZAP-configured browser at the testing frontend.
   For a manually configured browser, use a loopback ZAP proxy port such as `8081`,
   ensure these loopback URLs actually pass through the proxy, and trust ZAP's CA
   only in the test profile. Do not change the normal browser's proxy/trust settings.
2. Create one context named `DAM disposable ZAP`. Include **only** this regex:

   ```text
   ^https://127\.0\.0\.2:(3443|8443)(/.*)?$
   ```

   Keep every other host/port out of scope, including development URLs, Supabase,
   Google/CDNs and ZAP's own UI/API. Confirm History shows requests to port `8443`;
   verify `/api/account/me/` returns the role expected after login.
3. Log in normally and complete MFA. Browse lists/search, previews, signed downloads,
   uploads, versioning, metadata, tags, profile and monitoring as permitted by each
   role. Wait for the passive scan queue to empty. Use a fresh browser profile/ZAP
   session for each role, logging out between roles. Keep findings labelled by role.
4. Test unauthenticated, Viewer, Editor and Admin behaviour separately. A successful
   HTTP page render alone does not prove API authentication. Check the authenticated
   profile and API responses, and save representative request/response evidence
   with secrets redacted before sharing.

See ZAP's [modes](https://www.zaproxy.org/docs/desktop/start/features/modes/),
[Manual Explore](https://www.zaproxy.org/docs/desktop/addons/quick-start/),
[scope](https://www.zaproxy.org/docs/desktop/start/features/scope/), and
[authentication](https://www.zaproxy.org/docs/desktop/start/features/authentication/)
documentation.

## Controlled active scanning (manual decision, never launched by scripts)

After reviewing scope and passive results, use **Protected mode**, mark only the
above context in scope, and actively scan selected isolated API requests. Start with
one scanner thread, low strength and a delay around 1 second. Increase only after
checking server health. Keep the frontend's `/_next/` assets, HMR/dev endpoints and
third-party resources excluded from active scanning.

Initially exclude login/token/MFA, logout, signup, email verification/recovery,
account mutation, admin actions, destructive asset/tag operations, and large-upload
or resource-exhaustion checks. Exercise these deliberately as targeted manual tests
after saving evidence and confirming a reset is acceptable. Never use Attack mode
or an unrestricted recursive active scan against all discovered sites.

Browser cookies alone do **not** automatically authenticate an active scanner.
Configure and validate ZAP's supported browser/session authentication and CSRF handling
for the selected role before an authenticated scan. This app rotates refresh cookies,
enforces CSRF on mutations, binds media signatures to sessions, and requires TOTP.
A captured password/MFA POST cannot simply be replayed indefinitely. Check a control
request to `/api/account/me/` before/during scanning; stop on 401/403 or unexpected
identity. If reauthentication is needed, complete the normal MFA flow. Do not disable
MFA/CSRF, add token bypasses, or raise throttles to help the scanner. Treat expected
429s/account lockouts as security behaviour; pause and wait or reset disposable data.

Suggested targeted OWASP Top 10 coverage: cross-role API authorization and direct
object access; unauthenticated/private/signed media access; expired/tampered/reused
sessions and signatures; signup/verification/MFA/recovery; CSRF and cookie settings;
search/metadata input handling; upload type/filename/content/size rejection and
quarantine; SHA-256 tampering; and the Admin audit/alert view. Choose and record the
OWASP Top 10 edition required by your assessment. A scanner finding needs manual
validation; DAST does not establish complete Top 10 coverage.

## Verification and limits

`verify` runs targeted live HTTPS checks, not a scanner. It creates temporary synthetic
accounts, completes real CSRF/password/TOTP/refresh workflows, checks all three roles,
uploads/validates/downloads/edits/deletes an image, checks signed media authorization,
signup/captured verification and recovery email, logout, audit records and Next.js
route rendering. It deletes its own users/assets while retaining fixture accounts
and audit evidence. Its password/TOTP material stays in memory. Results are saved to
`.zap/state/verification-report.json`; reset removes the report. Captured messages
from verification are also disposable and may refer to already deleted test users.

Additional regression commands (these do not start an app or read development `.env`):

```powershell
.\.venv\Scripts\python.exe -B scripts/test_zap_isolation.py
.\.venv\Scripts\python.exe -B backend/manage.py test backend user asset --settings=backend.test_settings --verbosity 0
node --test frontend/src/utils/securityActivity.test.mjs
```

SQLite cannot reproduce PostgreSQL SQL syntax, privileges, RLS, collation or locking.
`select_for_update()` has no SQLite row-lock effect; IMMEDIATE transactions and a
20-second timeout serialize writers here without changing application security logic.
Use low concurrency. PostgreSQL injection payloads, race/locking results and
Supabase/platform controls require a future separate PostgreSQL/Supabase target.
See [Django's SQLite limitations](https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes).

The frontend uses Next's existing development runtime over HTTPS, so development
tooling/source-map findings are not production deployment findings. Browser visual
interaction, authenticator QR scanning, real MP4/GLB fixtures and actual ZAP scans
remain manual checks. Existing automated regressions cover additional media/security
cases, but are not a substitute for browser testing. TLS, server and header findings
also reflect the local TLS/WSGI adapter and testing-only CSP; confirm deployment
findings in a representative isolated deployment before labelling them production issues.

No dependency is downloaded. The existing 3D viewer script normally comes from a
Google CDN; isolated mode requests a local copy instead. Without a copy the app shows
its existing preview fallback; GLB validation, permissions and downloads remain in
place. If you already have the trusted model-viewer **4.0.0** bundle, place it at
`.zap/vendor/model-viewer.min.js` while stopped, then start again. Its external decoder
resources are also blocked; compressed models may need additional local resources.
PNG previews and downloads do not depend on this optional viewer.

## Return to normal development

Run `.\scripts\zap.ps1 stop`, close the dedicated browser/ZAP session, and restore any
manually changed browser proxy settings. Use your existing normal development startup
commands and original `127.0.0.1`/`localhost` URLs. No `.env`, main uploads, main database
or shell environment variables need restoration. The staged frontend and its build
cache never replace the normal frontend cache. Leave `.zap` ignored for another run,
or remove it only while stopped after checking its resolved path; it contains only
disposable local state.

Save generated ZAP exports in `reports/`, which is also git-ignored. Review and
redact request/response data before sharing reports as assessment evidence.
